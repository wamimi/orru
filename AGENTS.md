# Orru — project rules

Everything above this line is generated by `next dev` and will be rewritten.
Everything below is hand-maintained. Append here, not above.

**Orru** is trustless onchain income verification and credit, built on Creditcoin
with the Attestcoin protocol and Noir zero-knowledge proofs. Full context lives in
`docs/`: `SPEC.md` (product), `MVP.md` (scope, schedule, ownership),
`ATTESTCOIN.md` (technical reference), `INTEGRATION-HANDOFF.md` (the 19 Aug 2026
end-to-end proof), and `contracts/` (per-contract specifications).

Docs live at the repo root, never in `public/` — `public/` is served publicly by
Next.js, which would publish them on the deployed site.

## The architectural principle

Two layers that must never be confused:

- **FIND** (Etherscan / Alchemy) — searches for inbound transfers. **Convenience
  only. Nothing trusts it.**
- **PROVE** (Attestcoin) — builds a proof package, submits it to Creditcoin,
  verified against attested Ethereum history via the on-chain precompile.

> Etherscan finds it. Attestcoin proves it. Creditcoin never takes anyone's word.

If a credit decision ever depends on data that was not Attestcoin-verified, the
trusted middleman this project exists to remove has been reintroduced. That is
the whole differentiation. Treat any such change as a bug, not a shortcut.

## The two invariants — enforce and test in every contract touching attested data

**1. TRUSTED-SOURCE.** Never accept a source event merely because Attestcoin
proved it existed. Always additionally require that it came from the exact
expected source contract.

```solidity
require(log.address_ == TRUSTED_ANCHOR, "wrong source");
```

Without this, an attacker deploys their own contract, emits an identically
shaped event, obtains a genuine Attestcoin proof for it, and is accepted.

**2. SAME-COMMITMENT.** The value Attestcoin authenticated must be byte-identical
to the value used as a ZK public input. The same `bytes32` in both checks:

```solidity
require(registry.acceptedCommitment(pub[0]), "not attested");
require(verifier.verify(proof, pub), "bad proof");
```

Requiring two unrelated booleans is not composition. The binding is the security.

## The write layer — direction, shape, and what it does NOT give you

**Creditcoin → client chain only.** The write layer sends messages *out* to
Ethereum and other programmable chains. It never receives them. Anything flowing
*into* Creditcoin is readability.

```
user → dApp (source) → Outbox ─── Relayer (optional) ───▶ Inbox → Receiver → dApp
```

```solidity
interface IMessageReceiver {
    function receiveMessage(
        bytes32 messageId,      // unique per message
        uint256 chainId,        // which Creditcoin network sent it
        address emitterAddress, // the contract that sent it on Creditcoin L1
        bytes calldata payload  // dApp-specific; ABI for EVM→EVM
    ) external;
}
```

**Never let the application trust the Inbox directly.** Put an adapter between
them: the receiver checks `msg.sender == inbox`, the application checks
`onlyReceiver`. This is what lets a mock inbox be swapped for the real one by
replacing the receiver alone, and it is how we can build and demo the seam before
writability ships.

What the protocol does NOT do for you:

- **Validate `emitterAddress` yourself** against a trusted source set. This is
  the write-layer twin of TRUSTED-SOURCE: the protocol proves who sent it, the
  application decides whether that sender counts.
- **Ordering is not guaranteed** — delivery depends on sponsorship. If you need
  ordering, put a sequence number inside your payload and enforce it.
- **Design for reentrancy.** Delivery calls into your contract.
- **The payload is opaque** to the protocol. The outbox does not validate it.

What it DOES give you: **replay protection**. The inbox refuses to deliver the
same message twice, from any sender. That is one thing not to rebuild.

**Build the cross-chain surface for change** — upgradeable, or several composing
contracts. v2 features are expected. This does not apply to `PayerAnchor`, which
is deliberately immutable because it is a trust root.

## Hard constraints — non-negotiable

- **Attestcoin reads Ethereum only.** No Base, Polygon, Arbitrum, Optimism,
  Solana, Tron or BNB as *source* chains. Other-chain payments reach us only by
  the payer anchoring a commitment on Ethereum.
- **Source chain keys are NOT EVM chain ids.** On Creditcoin testnet: Ethereum
  Sepolia = **1**, Ethereum Mainnet = **3**. `11155111` appearing where a source
  chain key belongs is a bug.
- **Native query verifier precompile:** `0x0000000000000000000000000000000000000FD2`
- **Creditcoin testnet:** RPC `https://rpc.cc3-testnet.creditcoin.network`, chain id `102031`,
  explorer `https://creditcoin-testnet.blockscout.com`
- **The precompile establishes transaction inclusion and chain membership ONLY.**
  It does *not* check that the source transaction succeeded and does *not*
  interpret it. The application contract must check receipt status itself. A
  reverted transaction is still "included".
- **Attestcoin writability is NOT live and is NOT shipping during the hackathon.**
  Confirmed by the Creditcoin team: no testnet writability in this window, and no
  official Outbox/Inbox interfaces, mock inbox, example receivers or test vectors
  either. An interface stub is fine; a dependency is not. Phase 1 must be
  genuinely useful on its own. See "The write layer" below for the real shape.
- **Payer identity is `topics[1]`, never `from`.** `from` is the *gas payer*,
  which differs for router, relayer, multisig, smart-account and EIP-7702 flows.
  Reading `from` would attribute income to whoever paid gas — silent, and it
  looks like a registry bug when it surfaces.
- **`forge script` fails against Creditcoin testnet** — its block headers omit
  `prevRandao`. `bypass_prevrandao = true` is set in `foundry.toml` but is
  UNVERIFIED on forge 1.2.3. **Use `forge script` for Sepolia and `forge create`
  for Creditcoin**, which is what the proven 19 Aug pipeline did for every
  Creditcoin deployment.
- **Verification cost rises with event age** — roughly 10x after 24 hours. Process
  events while fresh.
- **USDC has 6 decimals, not 18.** 100 USDC is `100000000`. This is a likely bug.

## Toolchain — pinned, and pinned for a reason

| Tool | Version | Why pinned |
|---|---|---|
| solc | **0.8.27** | The generated `HonkVerifier` declares `^0.8.27` |
| optimizer_runs | **1** | At 200 the verifier is 59 bytes over the EIP-170 limit |
| bytecode_hash | **none** | Same reason — size |
| via_ir | **false** | `true` fails the verifier with a Yul stack-too-deep exception |
| nargo | **1.0.0-beta.18** | The version the 19 Aug pipeline was proven on |
| bb | **3.0.0-nightly.20260102** | Ditto. Paired with the above |
| @gluwa/usc-sdk | **0.18.0** exactly | Proven working |
| @gluwa/usc-contracts | **0.1.2** exactly | Proven working |

Changing any of these means re-running the full end-to-end compatibility smoke
test. Do not upgrade casually. Where docs and the proven pipeline disagree, **the
proven pipeline wins** — `ATTESTCOIN.md` §10 lists different versions and is stale.

## The commitment scheme — the silent killer

`shared/commitment.ts` is the single source of truth for encoding.

```
commitment = keccak256(abi.encode(recipient, amount, period, salt))
```

**`abi.encode`, not `abi.encodePacked`. 32-byte padded per field.** Noir must
mirror this exactly, and `keccak256` is used in-circuit specifically so Solidity
can recompute the identical value for the SAME-COMMITMENT invariant.

A Foundry test and a `nargo` test must compute the same commitment for the same
fixed inputs and assert equality. **If Solidity and Noir disagree, everything
compiles fine and nothing ever verifies — and the resulting bug looks completely
unrelated.** Nothing downstream starts until that test is green.

## Solidity standards

- Solidity 0.8.27, explicit visibility on everything
- **Custom errors, not revert strings**
- OpenZeppelin for ERC20 / Ownable / ReentrancyGuard; **SafeERC20 for every transfer**
- Checks-Effects-Interactions ordering
- No unbounded loops over user-supplied input
- Natspec on every external and public function, stating **who may call it and why**
- **Every contract ships with its test file in the same commit**
- Negative tests are the point: they are what prove the security properties

is Solidity. Always check `pwd` before writing.

`shared/commitment.ts` is the dangerous one — both the circuit and the frontend
depend on it, and a silent change breaks proof verification everywhere.

## Agent working rules

- **Never deploy.** Never run `forge script --broadcast`, `forge create --broadcast`,
  or `cast send`. A human deploys with an encrypted keystore (`--account cc3-deployer`).
- **Never commit and never push.** A human commits and opens PRs.
- **Stop and show the result** when `forge test` passes or fails.
- **Ask rather than guess** when a spec is ambiguous.
- Read `node_modules/next/dist/docs/` before writing frontend code — this Next.js
  differs from training data.

## Foundry gotchas already paid for

- Put `--broadcast` **before** `--constructor-args`. Forge's variadic parsing
  swallows flags that follow it and silently stays in dry-run.
- The generated verifier needs its linked library `ZKTranscriptLib` deployed
  first and passed via `--libraries`, or deployment fails on dynamic linking.
- `@gluwa/usc-contracts`' `EvmV1Decoder` is also an external library and needs
  the same treatment.
- Run `forge clean && forge build --sizes` before deploying any newly generated
  verifier.
- `forge install --no-git` — never add a git submodule to the parent repo.
- `contracts/lib/forge-std` is committed so a fresh clone builds;
  `contracts/node_modules/` is not. Bootstrap: `cd contracts && npm install`.
